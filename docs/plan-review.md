# Modernization plan review

1. 協議用計画として進行を止める指摘はない。`modernization-request.md` の依頼と追加指示、`modernization-plan.md` 全文、依存調査で開いた実ソースを照合した。実装差分は追加・削除とも 0 行という依頼時点の前提で、実装の安全性や性能を承認したものではない。テスト・ビルド・lint はこのレビューでは実施していない。

2. `Map[K comparable, V any]` / `New[K,V]()`、内部 item/pool への型伝播、rmap までの移行が明記され、ユーザーが目的としている API 変更に一致する。型なし API を包むだけの計画ではない。`MapHead.asItem[K,V]` はメソッド自身の型引数を使う具体的な接続点になっている。Go 1.27.1 の対応と最小コードの実行は母艦の確認結果を受領しており、このレビューによる独立再実行ではない。

3. bucket 階層、連続 pool、相対リンクを出発点として保持し、別実装への置換を既定にしていない。修正した測定器による旧新比較、値サイズ・キー分布・混合率・割り当て・GC・拡張境界が計画に含まれる。性能値や許容低下率を根拠なく確定していないため、性能維持という依頼と整合する。

4. GC 到達性、旧 reader の寿命、削除後再利用、公開済み item のコピー、並行履歴の検証を未解決事項として扱っている。これは elist_head の `ListHead.diffPtrTo` / `directNext` / `RepaireSliceAfterCopy`、loncha の `ListHead.Init` / `DirectPrev`、本体の `samepleItemPool._expand` / `_split` を開いて確認した懸念と一致する。checkptr 無効化を合格条件にせず、race 成功だけでも正しさを断定しない点を確認した。

5. 実装段階の具体化では `dependency-investigation.md` の移動先公開順、修復途中の失敗、所有配列からの index/offset 解決、固定 chunk という代案も設計判断へ反映する必要がある。これは今回の計画を差し戻す理由ではなく、順序 2 の所有権・同期設計と再現テストで解決すべき具体的な内容。相対差分の整数計算だけをもって依存修正完了とはできない。

6. 回帰、型、衝突、容量境界、並行操作、GC、逐次 fuzz と並行履歴、rmap の取得実値の検証が含まれ、追加されたテスト・ベンチ要求に対応している。型移行前の現行 API で表現できないケースは型付き API の段階で追加するという依存順で実施可能。強制 GC の不具合や性能懸念は現時点で実測済みの不具合と混同しないことが引き続き必要。

7. submodule は修正が必要な依存だけを対象にしており、ユーザーの許可範囲に収まる。実装開始前に詰める判断は、owner とリンクの持ち方、移動と再利用の条件、K のハッシュ、値更新の同期、低レベル API の型付き接続、Range の並行更新時の意味。計画はこれらを完成済みと偽っていない。追加の必須修正はない。
